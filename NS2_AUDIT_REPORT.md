## 3. In-Depth NS-2 Code Audit

### A. Audit of `simulation/sim.tcl`
- **Topology:**
  - Nodes: `client` (`0`), `router` (`1`), `server` (`2`), `attacker` (`3`).
  - Access Links: `$client $router 10Mb 5ms DropTail` and `$attacker $router 10Mb 5ms DropTail`.
  - Bottleneck Link: `$router $server 2Mb 10ms DropTail`.
  - Queue: DropTail FIFO queue with default buffer limit of 50 packets.
- **Traffic Representation:**
  - Legitimate (Flow 1): `Agent/TCP` with `Application/FTP`, packet size 1,000 bytes payload. NS-2 adds 40 bytes TCP/IP headers, resulting in 1,040-byte wire packets (and a 40-byte SYN packet).
  - Attack (Flow 2): `Agent/UDP` with `Application/Traffic/CBR`, packet size 40 bytes, transmission rate 5 Mbps ($5,000,000\text{ bps}$).
  - *Engineering Evaluation:* The attack stream is a UDP CBR flood, not a TCP SYN flood. It exhausts bandwidth and queue buffers, but does not model half-open TCP TCB state-table exhaustion.
- **Scenario Differences & Mitigation:**
  - `baseline`: Flow 1 runs from $t=0.0\text{s}$ to $10.0\text{s}$; Flow 2 is disabled.
  - `attack`: Flow 1 runs from $t=0.0\text{s}$ to $10.0\text{s}$; Flow 2 runs from $t=3.0\text{s}$ to $8.0\text{s}$ (5-second flood).
  - `mitigated`: Flow 2 starts at $t=3.0\text{s}$. At $t=4.0\text{s}$, `$ns rtmodel-at 4.0 down $attacker $router` shuts down the attack link, and `$flood stop` terminates transmission.
- **Metric Extraction:**
  - The embedded `analyze` procedure opens `results/$mode.tr`, filters events matching `event == "r"` and `to_node == 2`, categorizes bytes by `flow_id` (1 vs 2), aggregates into 0.5-second bins, and computes goodput in Mbps:
    $$\text{Goodput (Mbps)} = \frac{\text{Bytes in Bin} \times 8}{0.5\text{s} \times 1,000,000}$$
  - Results are saved to `results/${mode}_throughput.csv` and phase averages (0-3s, 3-8s, 8-10s) are printed.

### B. Audit of `simulation/sim_arp.tcl`
- **Topology:** 4 nodes (`client`, `router`, `server`, `attacker`).
- **Mechanism:**
  - Flow 1: Normal TCP FTP from `client` to `server`.
  - Flow 2: A diverted UDP CBR flow (1,000 bytes at 1 Mbps) from `client` to `attacker`.
  - In `normal`: Diverted flow never starts.
  - In `spoof`: Diverted flow runs from $t=3.0\text{s}$ to $10.0\text{s}$ ($7.0\text{s}$).
  - In `static`: Diverted flow runs from $t=3.0\text{s}$ to $5.0\text{s}$ ($2.0\text{s}$, modeling static ARP correction at $t=5.0\text{s}$).
- *Engineering Evaluation:* Wired NS-2 has no ARP cache or dynamic ARP protocol. This script provides an **illustrative behavioral model** of traffic diversion. Genuine ARP poisoning was validated via Scapy in `simulation/python_attacks/arp_spoof.py`.

## 4. Verification of Results & Mathematical Reconciliation

### A. Legitimate Goodput Event Breakdown (`mitigated.tr`)
Every packet received at Server node `2` for Flow 1 was extracted:
- **Total Packets Received:** Exactly **2,000 packets**.
- **Packet Sizes:**
  - 1 packet of 40 bytes (TCP SYN connection setup).
  - 1,999 packets of 1,040 bytes (TCP data segments: 1,000B payload + 40B header).
- **Total Bytes:** $(1 \times 40) + (1,999 \times 1,040) = 40 + 2,078,960 = \mathbf{2,079,000\text{ bytes}}$.
- **Full 10-Second Simulation Mean Goodput:**
  $$\frac{2,079,000 \times 8}{10.0 \times 1,000,000} = \mathbf{1.663200\text{ Mbps}}$$
- **Recovered Steady-State Throughput ($t \ge 5.0\text{s}$):**
  - In `mitigated_throughput.csv`, 8 out of 10 bins record **1.996800 Mbps** (120 packets of 1,040 bytes = $124,800\text{ bytes}$ per 0.5s bin):
    $$\frac{124,800 \times 8}{0.5 \times 1,000,000} = \mathbf{1.996800\text{ Mbps}} \quad (99.84\%\text{ of 2 Mbps})$$
  - Two bins ($t=6.5\text{s}$ and $t=9.0\text{s}$) record **2.013440 Mbps** (121 packets = $125,840\text{ bytes}$).
  - Over the full 5.0s steady-state window ($[5.0, 10.0)$), exactly 1,202 packets arrive, totaling $1,250,080\text{ bytes}$, yielding an average arrival rate of **2.000128 Mbps**.
  - **Independent Verification of the 80-Byte Discrepancy ($1,250,080 - 1,250,000 = 80\text{ bytes}$):**
    - **Configured Bottleneck Capacity:** $2,000,000\text{ bps}$. Over an exact $5.000000\text{s}$ window, nominal byte capacity is $\frac{5.0 \times 2,000,000}{8} = 1,250,000\text{ bytes}$.
    - **Observed Trace Receptions in $[5.0, 10.0)$:** Exactly **1,202 packets** are received at server node 2 (`event r`, `to_node 2`, `flow_id 1`).
    - **Packet Sizes:** All 1,202 packets are uniformly 1,040-byte TCP data segments ($1,202 \times 1,040 = 1,250,080\text{ bytes}$). No other packet size exists in this window.
    - **Reported Packet-Arrival Goodput:** $\frac{1,250,080 \times 8}{5.0 \times 1,000,000} = \mathbf{2.000128\text{ Mbps}}$ (80 bytes or 0.0064% above nominal capacity).
    - **Investigation of Trace Events Around Window Boundaries:**
      - The previous report attributed the start of transmission to $t = 4.998312\text{s}$. Trace inspection of `mitigated.tr` reveals this was a semantic misattribution:
        - At $t = 4.998312\text{s}$, the event logged is `r 4.998312 1 2 tcp 1040 ------- 1 0.0 2.0 795 17230`. This is the **reception completion** of the preceding packet (seq 795, pid 17230) at server node 2, NOT a transmission departure.
        - The first packet arriving inside the window (seq 796, pid 17232) actually began transmission departure at bottleneck router node 1 at $t = 4.988312\text{s}$ (`- 4.988312 1 2 tcp 1040 ... 796 17232`).
        - Its serialization completed at node 1 at $4.988312 + 0.004160 = 4.992472\text{s}$ (outside window).
        - Its leading edge reached the server after 10 ms propagation delay at $4.988312 + 0.010 = 4.998312\text{s}$ (outside window, exactly when packet 795 completed reception).
        - Full packet reception completed at server node 2 at $t = 5.002472\text{s}$ (`r 5.002472 1 2 ... 796 17232`, inside window).
      - The last packet arriving inside the window (seq 1997, pid 19625) completed reception at server node 2 at $t = 9.998632\text{s}$ (`r 9.998632 1 2 ... 1997 19625`).
    - **Origin of the 5.000320-Second Span:**
      - $9.998632 - 4.998312 = 5.000320\text{ seconds}$ is the inter-packet **reception interval** spanning 1,202 packet inter-arrivals ($1202 \times 0.004160\text{s} = 5.000320\text{s}$), measured from the completion of the packet preceding the window (packet 795) to the completion of the last packet in the window (packet 1997).
      - At router node 1, the transmission span for these same 1,202 packets was $9.988632 - 4.988312 = 5.000320\text{ seconds}$.
    - **Status of the 2.000000 Mbps Claim:**
      - Computing $\frac{1,250,080 \times 8}{5.000320 \times 1,000,000} = 2.000000\text{ Mbps}$ is a **mathematical inference** from the serialization rate of backlogged packets ($\frac{1040 \times 8}{0.004160} = 2,000,000\text{ bps}$), not an independent empirical trace measurement.
      - Over the fixed, continuous 5.000000-second measurement window $[5.0, 10.0)$, discrete packet-arrival goodput in the trace remains **2.000128 Mbps**.
    - **Audit Finding & Qualification:**
      - The 80-byte difference is NOT "fully resolved" as if the discrepancy vanished from the trace; it remains an inherent **measurement limitation of discrete packet-arrival binning over continuous time windows** (window boundary quantization artifact where 1202 discrete packets arrive within a continuous 5.0s window that nominally spans 1201.923 packet transmission intervals).
      - After mitigation, legitimate traffic approaches the configured 2 Mbps bottleneck capacity (~99.84% in modal 0.5s bins of 1.9968 Mbps), with the measured value depending on the measurement window alignment and throughput methodology.

### B. CBR Generation: Inferred Calculation vs. Observed Trace Events
- **Inferred from Configuration:**
  With packet size $S = 40\text{ bytes}$ and rate $R = 5,000,000\text{ bps}$, the serialization interval is $\tau = \frac{40 \times 8}{5,000,000} = 64.0\text{ }\mu\text{s}$, yielding an expected rate of **15,625 pkts/s**. Over 5.0 seconds, the expected generated count is $15,625 \times 5.0 = \mathbf{78,125\text{ packets}}$ (and $15,625 \times 1.0 = \mathbf{15,625\text{ packets}}$ for 1.0s).
- **Observed Empirical Trace Events:**
  - *Unmitigated Attack (`attack.tr`):* Exactly **78,125 enqueue (`+`) events** are logged for Flow 2 at attacker node 3 on link $3 \rightarrow 1$. At the bottleneck router link $1 \rightarrow 2$, exactly **47,156 drop (`d`) events** and **30,969 dequeue (`-`) / receive (`r`) events** are recorded at server node 2.
    $$\text{Observed Conservation: } 47,156\text{ drops} + 30,969\text{ received} = \mathbf{78,125\text{ packets (100.00\% empirical balance)}}$$
  - *Mitigated Attack (`mitigated.tr`):* Exactly **15,625 enqueue (`+`) events** are logged for Flow 2 at node 3. Logged drops total **9,688** (9,610 on link $1 \rightarrow 2$ and 78 on link $3 \rightarrow 1$ when link shut down at $t=4.0\text{s}$), and logged server receptions total **5,937**.
    $$\text{Observed Conservation: } 9,688\text{ drops} + 5,937\text{ received} = \mathbf{15,625\text{ packets (100.00\% empirical balance)}}$$

### C. Analysis of Packet Drops by Flow and Node
- **`attack.tr`:**
  - Total Drops: **47,180** (Flow 2: 47,156; Flow 1: 24).
  - All 47,180 drops occurred on bottleneck link `('1', '2')`.
  - *Explanation:* When the 5 Mbps flood saturates the router's 50-packet FIFO DropTail queue, arriving legitimate Flow 1 packets are dropped alongside attack packets.
- **`mitigated.tr`:**
  - Total Drops: **9,710** (Flow 2: 9,688; Flow 1: 22).
  - Drop Locations: 9,632 on bottleneck link `('1', '2')` (9,610 Flow 2 + 22 Flow 1) and 78 on link `('3', '1')` (all Flow 2 packets dropped at the attacker-to-router interface when the link drops at $t=4.0\text{s}$).

## 8. Unresolved Issues and Limitations

1. **Transport Protocol Approximation:** NS-2 `sim.tcl` models UDP/CBR queue congestion (40-byte packets at 5 Mbps) rather than genuine TCP SYN half-open connection exhaustion (operating system TCP TCB table memory starvation).
2. **Layer 2 Protocol Fidelity & ARP Model:** Wired NS-2.35 point-to-point links do not support dynamic broadcast ARP resolution or ARP caches. `sim_arp.tcl` is strictly an illustrative behavioral traffic-diversion model, not native ARP cache poisoning.
3. **Scapy Script Execution Status:** The existence of `simulation/python_attacks/arp_spoof.py` and `mac_flood.py` demonstrates attack frame construction syntax, but does NOT prove live network execution, kernel packet transmission, or successful packet interception on any target host.
4. **MAC Flooding Figures as External Benchmarks:** MAC-flooding metrics (97,657 sent, 9,001 leaked, 977 frames to shutdown) remain unverified external report benchmarks because NS-2 lacks switch CAM table simulation logic and no raw PCAP or CAM trace artifacts exist in the repository.
5. **No Fresh Native NS-2 Execution on macOS:** No fresh native NS-2 execution on the local macOS ARM64 host has been performed or confirmed; local verification is based on automated parsing and mathematical reconciliation of the existing trace files (`baseline.tr`, `attack.tr`, `mitigated.tr`). Fresh execution requires Docker or an Ubuntu 20.04 LTS environment.
6. **No Packet Tracer `.pkt` or Live Capture Artifacts:** No Cisco Packet Tracer `.pkt` topology files or raw `.pcap` capture files were found in the project repository. All Packet Tracer configurations and Wireshark tables represent reference configurations and structured demonstration records.
